# The Weekly Loop

**So what:** One repeatable cycle — log the lesson, review what saves, plan the next class — is the whole beta product.

The interface keeps this simple: **chat on the left, editable draft on the right, teacher review before durable writes.**

> [!blueprint]
> **The weekly loop**
> 1. **Update memory** after teaching (or correct an existing lesson).
> 2. **Review** proposed file changes — approve only what you trust.
> 3. **Create lesson plan** for the next class from approved memory.
> 4. **Save the plan** to a lesson date — then teach it and loop again.

## Update memory

Use **Update memory** after class or when correcting a lesson record.

The copilot turns your conversation into structured lesson results. It uses class context and lesson evidence, but **does not write durable wiki memory until you approve** proposed file changes.

A strong memory update usually includes:

- what was taught and what students understood
- where they struggled and what worked
- homework, tests, open loops, or follow-ups
- anything that should shape the next lesson

> [!tip]
> From the timeline: planned lessons → **Add lesson results**; taught lessons → **Correct with agent**. If the date is known, the target may already be selected. If not, confirm the date in chat before saving.

## Create lesson plan

Use **Create lesson plan** when preparing the next lesson.

The planner reads class memory, recent lessons, open loops, misconceptions, and teaching patterns. It updates the plan draft only — **planning chat does not write class memory.**

Good requests can be plain teacher language:

- “Plan the next 45-minute lesson after the redox review.”
- “Prepare a lesson that checks oxidation-number assignment.”
- “Make this more active; they struggled with balancing last time.”

The saved plan appears on the lesson date. After you teach it, use **Add lesson results** to log what actually happened.

## Review before you save

Review is the trust layer. Chat can draft; **durable changes require your approval.**

### Before saving memory

- Is the lesson date correct?
- Does the diary match what actually happened?
- Are open loops and misconceptions specific enough for next week?
- Is anything too sensitive or student-specific?
- Are the changed wiki files worth keeping?

> [!warning]
> Do not save if the lesson date is wrong. Correct the date or restart from the intended timeline entry. A wrong saved fact can mislead future plans.

### Before saving a plan

- Does the plan fit the available time?
- Does it reflect recent class memory?
- Are activities realistic for your room and materials?
- Are misconceptions and open loops handled directly?

Reject or edit changes that are wrong. **Do not save memory just because the draft looks polished.**

> [!important]
> When you save, KlassenPilot updates the approved class wiki. A small correction now improves future plans; a wrong saved fact misleads later work.

## What saves where

| Action | What gets saved |
|--------|-----------------|
| Update memory (after approval) | Lesson results and related class memory files |
| Create lesson plan (after save) | Plan file on the chosen lesson date |

Both workflows keep durable writes explicit. Planning never silently updates memory; memory update never skips your review.
