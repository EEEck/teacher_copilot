Living epic / tracking home for **class materials upload** (textbook + personal).
Not a task-by-task implementation plan yet — that comes after design-section
approval. Product strategy: [`docs/pm_hub.md`](../docs/pm_hub.md). Roadmap row:
[`product_backlog.md`](product_backlog.md) § v1.2.

`material_ids`, summary stub, table image sidecar, scratch-outside-wiki).
Year-start class library browse / “use chapter 1” global search = follow-up.

---

## Purpose

Let a teacher upload photographed, scanned, or PDF material into a class and get
OCR'd, reviewable, citable content for planning — without retyping and without
silently writing durable class memory.

## Scope (first slices)

- **In-plan upload first** (year-start library designed now, built later).
- Two sibling arms: **Textbook** (chapterized) vs **Personal** (per-lecture /
  lesson-linked), chosen by a UI toggle on upload.
- OCR via **Mistral OCR 4 only** for the first runtime slice.
- Plan-scratch artifacts → promote into class materials on save /
  keep-in-materials.
- Materials as a **source/citation layer**, separate from curriculum
  `wiki/sources` trusted sources (reuse mechanics, not the same registry/tools).

## Non-goals

- Autonomous conversion of uploads into durable wiki facts.
- LlamaParse (or other third-party OCR vendors) in the first slice.
- Docling as a first-slice runtime dependency (later optional backup only).
- Open-web / “all textbooks” corpus before licensing constraints are solved.
- Vector DB as the default retrieval path.
- Full year-start library UX before in-plan upload works end-to-end.

## Architecture sketch (Option 1)

### Wiki layout (current)

```
wiki/classes/{class_id}/
  materials/
    textbooks|personal/
      {material_id}/
        source.pdf                 # original upload (reference only)
        summary.md                 # wiki-friendly stub + inventory
        document.agent.md          # assembled OCR MD
        assets/
          manifest.json
          img-*.jpeg
          tbl-*.html
          tbl-*.jpg                # PDF table bbox crops (Lewis etc.)
        important_images.json
        provenance.json            # checksum/model/usage; NO base64
  lessons/{YYYY-MM-DD}/
    lesson_plan.md
    materials.json                 # { "material_ids": ["..."] }
```

Curriculum trusted sources remain under `wiki/sources` (LehrplanPLUS, etc.).
Class materials never share that registry id space.

### Plan-scratch lifecycle

1. Teacher uploads in Plan (toggle Textbook vs Personal).
2. Backend runs Mistral OCR 4 → writes **session/plan scratch** artifact trio
   (not yet durable class materials).
3. Planner may read scratch via materials-scoped tools / context (compact TOC +
   progressive section read; raw behind `raw_ref`-style capture).
4. On **plan save** and/or explicit **keep in materials**, promote scratch into
   `materials/{textbooks|personal}/{id}/`.
5. Discarded plans / abandoned uploads GC scratch (policy TBD in design plan).

### Promote rules (draft)

- Promote copies (or moves) the artifact trio + provenance into the class
  materials tree.
- Personal materials should carry optional **lesson / date link** when known.
- Textbooks carry chapter/section TOC suitable for progressive read.
- Plan-scoped-only imports stay flagged and must not look like standing library
  entries until promoted.
- Promotion never writes `course_state`, roster, diary, or other curated memory
  pages.

### Context packs / tools (separation from trusted sources)

- Reuse the proven pattern: compact TOC/index in context; list/search/read tools;
  provenance on citations.
- **Do not** overload `trusted_sources.md`, `list_trusted_sources`, or
  `wiki/sources` paths.
- New materials index + tools (names TBD in implementation plan), e.g. class
  materials TOC pack + `list/search/read_class_material` (illustrative).
- Citation namespace must distinguish materials vs curriculum sources vs class
  memory wiki pages.

### Memory-safety

- Default: materials are evidence/citation, not compiled class memory.
- Durable memory facts still flow only through Update Memory / MemV4
  (`remember` → ledger → Sweep → teacher-approved apply).
- Plans should paraphrase/adapt into self-contained lesson text; end citations
  stay light (page/section pointers), assuming the teacher has the material.

## Open questions / risks

| Topic | Question / risk | Owner hint |
|---|---|---|
| **Copyright / licensing** | What may be stored (full OCR vs chapter excerpts)? School-owned vs publisher textbooks? Retention? | Product / legal |
| **EU data residency** | Mistral Files + Batch region/residency for German teachers; retention of uploaded bytes | Platform |
| **Page index 0 vs 1** | Mistral API pages are **0-based**; teacher-facing citations usually 1-based — pick a single display/contract rule | Eng design |
| **Citation namespace** | How materials ids appear vs `wiki/sources` vs wiki page paths in plans | Eng design |
| **Image bloat** | Keep `important_images.json` small; GC policy for scratch page images | Eng |
| **Naming clash** | Plan “Student Materials” (handouts in the lesson) vs class **materials** library — UI copy must disambiguate | Product / UI |
| **Scratch GC** | When do abandoned plan-scratch OCR jobs/files expire? | Eng |
| **Personal ↔ lesson link** | Required vs optional date/lesson binding on promote | Product |
| **Textbook chapterize** | Who cuts chapters — model annotation, heuristic TOC, or teacher confirm? | Phase 3 design |
| **Docling trigger** | When (if ever) to offer Docling backup UX vs silent fallback | Later |

## Explicit note: Docling deferred

**Docling is not part of the first runtime slice.** It remains a later optional
backup for born-digital PDFs and offline / self-hosted extraction paths.
Roadmap wording should say: primary OCR = **Mistral OCR 4**; Docling = later
optional backup — not co-equal first-slice engines. No LlamaParse in v1.2 first
slice.
